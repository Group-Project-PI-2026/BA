# Розділ 1: Вступ та цілі (Introduction and Goals)

Цей документ описує архітектуру системи бронювання апартаментів та керування короткостроковою орендою. Мета системи — забезпечити зручний пошук та безпечне бронювання житла для орендарів, надати інструменти управління об'єктами для менеджерів і власників, а також забезпечити автоматичну інтеграцію з зовнішніми готельними системами.

## 1.1. Призначення системи та бізнес-ролі (Рольова модель)

Система використовує єдиний веб-інтерфейс (1 UI) у вигляді React SPA. Видимість розділів та доступ до функцій визначається ролями користувача (RBAC):

- **Орендар:** Пошук апартаментів за датами/фільтрами, перегляд доступності, оформлення бронювання з тимчасовим резервуванням, оплата, отримання інструкцій із заселення через веб-сайт.
    
- **Власник:** Подання заявки на співпрацю для додавання житла в систему, перегляд статистики своїх об'єктів.
    
- **Менеджер:** Управління каталогом апартаментів (CRUD), управління єдиним календарем зайнятості, зміна статусів бронювання, обробка заявок Власників.
    
- **Адміністратор:** Керування системою в цілому, призначення ролей користувачам (наприклад, надання прав Менеджера), доступ до логів та моніторингу працездатності через Grafana.
    
- **Інтеграція з іншими готелями (Channel Manager):** Автоматичний двосторонній обмін даними про доступність та бронювання з зовнішніми готельними системами для підтримки єдиного актуального календаря та уникнення крос-платформенних подвійних бронювань.
    

## 1.2. Цілі якості (Quality Goals)

| **Пріоритет** | **Атрибут якості**   | **Опис**                                                                                                                             |
| ------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1             | **Цілісність даних** | Абсолютна неможливість подвійного бронювання одних і тих самих дат (як всередині системи, так і через зовнішні готелі).              |
| 2             | **Надійність**       | Помилки сторонніх сервісів (еквайрингу чи зовнішніх готелів) не повинні призводити до втрати статусу бронювання чи хибних скасувань. |
| 3             | **Безпека**          | Захист персональних даних та інструкцій; суворе розмежування прав доступу на основі JWT/OIDC.                                        |
| 4             | **Швидкодія**        | Пошук в межах 500ms та перевірка доступності дат без затримок.                                                                       |

- **Інтеграція з іншими готелями:** Наявність модуля Channel Manager API для синхронізації доступності із зовнішніми готельними системами.

# Розділ 3: Контекст системи (Context View)

Цей розділ описує зовнішнє оточення Системи бронювання апартаментів. Він визначає користувачів, які взаємодіють із системою, та зовнішні сервіси, від яких вона залежить.

![[1.drawio 3.png]]

## 3.1. Бізнес-контекст (Business Context)

**Опис суб'єктів та зовнішніх систем:**

1. **Користувачі (Орендар, Власник, Менеджер, Адміністратор):** Взаємодіють із системою через єдиний веб-інтерфейс, де функціонал адаптується відповідно до призначених ролей.
    
2. **Автентифікаційний сервіс (Keycloak):** Виділений IAM-сервіс, який відповідає за автентифікацію користувачів, видачу токенів (OIDC) та управління обліковими записами.
    
3. **Платіжний шлюз (Stripe):** Зовнішня система для обробки банківських карток. Повідомляє нашу систему про результати транзакцій через асинхронні Webhook-виклики.
    
4. **Зовнішні готелі / Сервіси оренди (Channel Manager API):** Зовнішні майданчики, з якими проводиться двостороння синхронізація зайнятості дат для підтримки єдиного актуального календаря.
    
5. **Поштовий шлюз (SMTP):** Сервіс для надсилання електронних листів із підтвердженнями бронювань, кодами авторизації та інструкціями із заселення.
    

## 3.2. Технічний контекст (Technical Context)

Усі зовнішні інтеграції базуються на стандартних захищених веб-протоколах:

- **Клієнтський доступ:** Взаємодія браузера з системою відбувається виключно через **HTTPS (порт 443)**.
    
- **Автентифікація та Авторизація:** Обмін даними між React SPA, бекендом та Keycloak реалізовано за протоколами **OpenID Connect (OIDC)** та **OAuth 2.0** із використанням JWT-токенів. Для доступу адміністраторів до Grafana використовується **SAML 2.0 / OAuth2 SSO**.
    
- **Інтеграція зі Stripe:** Ініціалізація платежу відбувається через генерацію `Stripe Checkout Session` на .NET бекенді. Отримання результату транзакції здійснюється через **Server-to-Server Webhook** (`POST /api/webhooks/stripe`) із обов'язковою перевіркою криптографічного підпису (`Stripe-Signature` HMAC-SHA256).
    
- **Інтеграція з іншими готелями:** Обмін даними про доступність дат виконується через захищений **REST API / Webhooks** із використанням API-ключів або OAuth2-токенів доступу.

## 5.1. Структура системи (Контейнери)

Внутрішня архітектура є модульною:

- **IAM (Keycloak)** є єдиною точкою автентифікації, управління ролями та збереження облікових записів.
    
- **Core API (.NET)** містить бізнес-логіку, модуль `Channel Manager API` для синхронізації з іншими готелями, інтеграцію зі Stripe та фонові задачі.
    
- **PostgreSQL** виступає єдиним реляційним сховищем (включаючи таблицю `booking_locks` для уникнення подвійних бронювань без використання Redis).



    ![[2 2.png]]

## 5.2. Опис компонентів

1. **Frontend Application (React SPA)**
    
    - **Технології:** React, TypeScript/JavaScript, HTML5, CSS3.
        
    - **Відповідальність:** Єдиний інтерфейс користувача (1 UI) для всіх ролей. Динамічно адаптує меню та доступні функції (пошук, бронювання, управління об'єктами, адміністрування) на основі ролей (RBAC), витягнутих із JWT-токена від Keycloak. Взаємодіє з Core API через REST.
        
2. **API Gateway / Web Server (Nginx)**
    
    - **Технології:** Nginx.
        
    - **Відповідальність:** Термінація SSL/TLS (HTTPS на порту 443), роздача статичних файлів зкомпільованого React SPA. Маршрутизація запитів (Reverse Proxy) до .NET API (`/api`), Keycloak (`/auth`) та Grafana (`/grafana`).
        
3. **Identity & Access Management (Keycloak)**
    
    - **Технології:** Keycloak.
        
    - **Відповідальність:** Управління обліковими записами користувачів, автентифікація через протокол OIDC (OpenID Connect) із видачею JWT-токенів. Забезпечення SSO (Single Sign-On) за протоколами SAML 2.0 / OAuth2 для доступу адміністраторів до Grafana.
        
4. **Core API & Background Tasks (C# .NET)**
    
    - **Технології:** .NET Core (C#), Entity Framework Core, Serilog.
        
    - **Відповідальність (API):** Обробка бізнес-запитів (каталог, календар, бронювання). Перевірка підписів та ролей у JWT-токенах від Keycloak. Інтеграція зі Stripe (Checkout Sessions & Webhook signature validation). Інтеграція з іншими готелями через `Channel Manager API`.
        
    - **Відповідальність (Worker):** Фонові задачі (`IHostedService`) для перевірки та очищення протермінованих тимчасових блокувань у `booking_locks`, а також надсилання сповіщень через SMTP.
        
5. **Primary Database (PostgreSQL)**
    
    - **Технології:** PostgreSQL.
        
    - **Відповідальність:** Надійне зберігання постійних даних (апартаменти, календар, бронювання, користувачі Keycloak у виділеній схемі). Гарантія відсутності подвійних бронювань через ACID-транзакції та таблицю тимчасових резервів `booking_locks` із полем `expires_at`.
        
6. **Prometheus**
    
    - **Відповідальність:** Збір (scrape) метрик продуктивності з .NET API (`/metrics`), PostgreSQL та системних ресурсів Docker-контейнерів.
        
7. **Loki (+ Promtail)**
    
    - **Відповідальність:** Збір агентом Promtail логів з `stdout`/`stderr` усіх контейнерів та їх централізоване збереження у Loki.
        
8. **Grafana**
    
    - **Відповідальність:** Візуалізація метрик із Prometheus та пошук логів за `Correlation ID` у Loki. Доступ авторизується через Keycloak.

# Розділ 6: Подання під час виконання (Runtime View)

У цьому розділі описано динаміку взаємодії компонентів під час виконання ключового бізнес-процесу системи: **оформлення бронювання з тимчасовим утриманням дат та його подальша оплата**.

Сценарій демонструє, як система гарантує відсутність подвійних бронювань (Data Integrity) без використання Redis, покладаючись на ACID-транзакції PostgreSQL та таблицю тимчасових резервів `booking_locks`.

## 6.2. Опис кроків та обробка виняткових ситуацій

1. **Ініціалізація (Кроки 1–2):** Орендар вибирає дати в React SPA та натискає "Забронювати". Фронтенд надсилає запит `POST /api/bookings/reserve` до .NET API, додаючи JWT-токен у заголовок `Authorization`.
    
2. **Перевірка та блокування в БД (Кроки 3–5):** .NET API перевіряє таблиці `bookings` (підтверджені деталі) та `booking_locks` (активні резерви) на наявність перетинів обраних дат.
    
    - Якщо дати вільні, бекенд створює запис у таблиці `booking_locks` з часом життя `expires_at = NOW() + 15 хвилин`.
        
    - Якщо дати зайняті, бекенд повертає помилку `409 Conflict`, і користувач бачить сповіщення в UI.
        
3. **Створення платіжної сесії (Кроки 6–9):** .NET API звертається до Stripe API й створює `Stripe Checkout Session`. Отриманий унікальний URL повертається на React SPA, який виконує перенаправлення Орендаря на захищену сторінку оплати Stripe.
    
4. **Обробка платежу та Webhook (Кроки 10–15):**
    
    - Орендар вводить дані картки на боці Stripe.
        
    - Після успішного списання коштів Stripe надсилає асинхронний Server-to-Server Webhook (`POST /api/webhooks/stripe`) з подією `checkout.session.completed`.
        
    - .NET API перевіряє підпис `Stripe-Signature`. Після успішної валідації у межах єдиної ACID-транзакції в PostgreSQL створюється запис у таблиці `bookings` (статус «Оплачено») та видаляється відповідне тимчасове блокування з `booking_locks`.

## 7.1. Огляд та мотивація інфраструктури

Система розгортається у хмарному середовищі **AWS (Amazon Web Services)** на базі віртуальної машини (Amazon EC2). Для оркестрації та ізоляції сервісів використовується `docker-compose`.

Відмова від Next.js та Redis дозволила спростити інфраструктуру: Nginx самостійно віддає статичні файли React SPA та проксіює запити до контейнерів .NET API, Keycloak і Grafana.

2. **Private Network (`Internal`):** Ізольована мережа без прямого доступу з інтернету. У ній знаходяться PostgreSQL, Prometheus та Loki.

# Розділ 8: Наскрізні концепції (Cross-cutting Concepts)

## 8.1. Стратегія логування (Logging)

У системі застосовується підхід централізованого структурованого логування:

1. **Формат логів:** Усі бекенд-сервіси генерують логи виключно у форматі **JSON** (з параметрами `booking_id`, `user_id`, `Correlation ID`).
    
2. **Логування на рівні додатків:**
    
    - **.NET API:** Використовує бібліотеку `Serilog` для запису логів у `stdout`.
        
    - **Keycloak:** Логує події безпеки (спроби входу, видача токенів, зміни ролей).
        
    - **Nginx:** Пише JSON access logs (URL, статус відповіді, час обробки).
        
3. **Агрегація (Log Aggregation):** Агент **Promtail** збирає логи з Docker-контейнерів і відправляють у сховище **Grafana Loki**.
    

## 8.2. Відстеження запитів (Correlation ID)



Для відстеження життєвого циклу запитів через усі контейнери використовується заголовок `X-Correlation-ID`:

1. При надходженні HTTP-запиту від React SPA, Nginx або .NET API генерує унікальний заголовок `X-Correlation-ID` (UUID).
    
2. .NET API автоматично прокидає цей ID крізь усі шари додатка та додає його до кожного рядка логів.
    
3. **Відображення та пошук (Де відображаємо):** Адміністратор або розробник відкриває **веб-інтерфейс Grafana**, переходить у **вкладку Explore**, обирає джерело даних **Loki** і вводить у пошук потрібний ID:
    
    Фрагмент коду
    
    ```
    {app="net-api"} |= "X-Correlation-ID: a1b2c3d4-e5f6-7890"
    ```
    
    У результаті в єдиній часовій шкалі відображається весь шлях запиту: від отримання в Nginx до виконання SQL-запиту в PostgreSQL та відповіді Stripe Webhook.
    

## 8.3. Моніторинг та Метрики (Metrics)

- **Збір метрик (Prometheus):** .NET API експортує метрики продуктивності на ендпоінт `/metrics`. Prometheus періодично опитує (scrape) цей ендпоінт, а також збирає метрики використання ресурсів Docker (CPU, RAM).
    
- **Візуалізація (Grafana):** Дашборди Grafana відображають RPS (кількість запитів/сек), відсоток помилок (4xx/5xx), Latency (95-й та 99-й перцентилі часу відповіді) та стан пулу з'єднань PostgreSQL.
    

## 8.4. Перевірки працездатності (Health Checks)

- **.NET API** має вбудований ендпоінт `/health`, який перевіряє стан бекенду та підключення до PostgreSQL.
    
- **Docker Engine** налаштований на регулярний опит `/health` (директива `healthcheck` у `docker-compose`). У разі збою Docker автоматично перезапускає контейнер.
